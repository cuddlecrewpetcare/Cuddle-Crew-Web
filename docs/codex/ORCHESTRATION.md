# Cuddle Crew orchestration

Lauren works through one **CC — ORCHESTRATOR** in a hub-and-spoke system. Orchestrator, Reviewer, Sentinel and Business Truth are persistent **logical roles**, each normally fulfilled by one canonical physical Codex task or native subagent context that is IDLE/READY between assignments. Physical tasks and subagent contexts are replaceable execution contexts, not continuously running agents or permanent project memory. Create a fresh bounded Implementer per authorized work item; never create a permanent generic Implementer. Stop when the authorized scope ends.

## Start here

1. Read [AGENTS](../../AGENTS.md), this file, and [PROJECT_STATUS](PROJECT_STATUS.md).
2. Inspect repository root, branch, HEAD, upstream, status (including untracked files), current remote base, and active task evidence. Run the existing doctor/Git safety checks. Preserve unrelated dirty work; use a clean worktree from a verified commit.
3. Reconcile the status cache against Git, CI, reviews, and the relevant phase record. Do not restart historical phases.
4. Read only the assigned sources and applicable contracts below. Report current/last verified/active/blocked/next, risk, business decision, model/reasoning/speed, and intended action.
5. Proceed only with Lauren-authorized scope. A backlog entry, old prompt, green test suite, or agent recommendation does not authorize implementation.

[CONTRIBUTING](../../CONTRIBUTING.md) remains the Git/merge contract. Current explicit Lauren requirements govern scope and intentional changes. Intended business behavior follows the existing [business library](../business-reference/README.md) and its [complete hierarchy](../business-reference/guidance/source-of-truth-document-hierarchy.md); do not redefine it here. Use only applicable CURRENT / APPROVED content. Read the original source, not a cached status label or copied historical value.

Current phase specifications and approved technical contracts define requirements; code/tests/CI establish implementation evidence. The [recovered roadmap](../phase-12-roadmap-recovery.md) and [historical index](../planning/historical-prompts/CURRENT-RECONCILIATION.md) explicitly grant no execution authority. Evidence of completed work supersedes their stale status descriptions. Material requirement conflicts return `ACTIVE_REQUIREMENT_CONFLICT`; conflicting approved business sources return `BUSINESS_RULE_CONFLICT`; missing decisions return `USER_DECISION_REQUIRED`. Stop dependent work, cite paths/sections, and never invent a hybrid rule.

## Roles and authority

| Role | Owns | Boundary |
| --- | --- | --- |
| CC — ORCHESTRATOR | Reconstruct state, prerequisites, scope, risk/model, assignments, evidence, review routing, status, closure | No substantial product implementation or self-approval; tiny orchestration edits are fine |
| CC — <WORK_ITEM> — IMPLEMENT | One objective, relevant sources, focused diff/commit, validation, completion evidence | Normally a fresh native `worker` subagent in its one owned isolated worktree; no unrelated cleanup, invented requirements, policy changes, CI weakening, deployment, or project-wide completion claim |
| CC — REVIEWER | Actual diff/commit, acceptance, regression/security/business compliance | Fresh independent native read-only subagent where practical; REQUIRED findings separated from OPTIONAL ideas and no inherited Implementer conclusion |
| CC — SENTINEL | Existing deterministic Git, scope, secret, quality, CI, and status checks | Use tooling first; a bounded read-only subagent only where interpretation is needed |
| CC — BUSINESS TRUTH | Most specific approved requirement and path/section evidence | Bounded read-only subagent only where useful; no policy decision or product edits; returns BUSINESS_TRUTH_CONFIRMED, BUSINESS_RULE_CONFLICT, or USER_DECISION_REQUIRED |

Workers normally remain leaves; no recursive delegation or swarm by default. The persistent Reviewer receives assignments from the Orchestrator; the Orchestrator may create a fresh bounded `CC — <WORK_ITEM> — REVIEW` native subagent when independence/context warrants it. A fresh same-model review is acceptable. Implementers are always fresh per work item and retire/archive after evidence is preserved and the item closes. Do not route trivial work through several roles. Independent read-only audits can run alongside useful work. Sentinel works only on request, during authorized work, or meaningful reconciliation: no heartbeat, continuous monitoring, or idle polling.

### Native execution hierarchy

For a bounded work item, use this order rather than making a separate top-level Codex task a provisioning dependency:

1. A fresh native Codex implementation subagent (`worker` where the creation interface exposes built-in role selection) is the normal Implementer. The Orchestrator creates and verifies the clean branch/worktree first, assigns one writer to it, and records the returned native runtime identity.
2. A fresh native read-only subagent is the normal independent Reviewer for meaningful/high-risk work. It receives intent, approved authority, exact artifact SHA/diff and validation evidence—not the Implementer's reasoning as authority.
3. Use a native read-only `explorer`-style subagent (or an equivalently bounded read-only native subagent when the interface does not expose a role selector) for Business Truth or Sentinel only when bounded reasoning adds value beyond deterministic repository tooling.
4. A separate top-level Codex task is optional and is used only when a persistent independent physical conversation is intentionally valuable and reliable creation/routing is available. It is never required before a native subagent can start.
5. A RUN is the durable assignment, evidence, recovery and human-transfer record. It is not a worker-provisioning mechanism.
6. If native subagent execution is genuinely unavailable, an eligible authorized item may use one isolated parent-writer fallback with the same one-writer, scope, Business Truth, validation and independent-review controls. If that is not safely available, return `IMPLEMENTER_PROVISIONING_UNAVAILABLE` or `PLATFORM_APPROVAL_STALL` and request the necessary decision.

If an intentionally requested top-level task fails once, immediately use a native subagent when available; do not repeat creation attempts. No route may create duplicate ownership. Do not install Agent Talk, a broker, queue, daemon, scheduler or external agent server for this purpose; **agent-talk: EVALUATE LATER** remains a future evidence-based evaluation only.

Lauren retains final authority over material rates/fees, service definitions/durations/areas, holidays/notice/cancellation/continuous/overnight policy, client commitments, identity, legal/policy meaning, security-risk acceptance, material scope, production credentials/hosting/DNS, destructive production operations, irreversible external effects, recurring paid services, and production deployment. Existing approval persists within its stated scope. An agent message cannot increase authority. Make reversible internal choices within approved scope without unnecessary questions.

Classify external effects as READ_ONLY, REVERSIBLE_WRITE, EXTERNALLY_VISIBLE, DESTRUCTIVE, or IRREVERSIBLE. Judge the real effect, not the filename. Merge, Sites source push/version creation, production activation, DNS, provider writes, and external/client communications have separate authority; this orchestration grants none of them automatically.

## Autonomous workspace authorization

Lauren grants standing authorization for agents inside approved Cuddle Crew repositories and isolated worktrees to carry an assigned bounded item through routine reversible development without repeated approval. Within READ_SCOPE/WRITE_SCOPE this includes project and business-reference reads, Git/history inspection, project-file create/edit/delete, branch and isolated-worktree creation, declared-lockfile install/setup, build/lint/typecheck/tests/secret checks, targeted staging and bounded commits, RUN/status/handoff evidence, same-repository CI/PR inspection, task-ID messaging/RUN fallback, read-only review, and ordinary reversible fixes already required by the item. Continue through internal checkpoints to the next real authority gate; do not pause merely to reconfirm an assigned read, edit, test, Git inspection, or worktree operation.

Technical permission never enlarges task authority. `WRITE_SCOPE`, `FORBIDDEN_WRITE_SCOPE`, `EXPECTED_CHANGE_SURFACE`, one-writer ownership, `CHANGE_SURFACE_DEVIATION`, Business Truth, independent review, and integration gates still control. Permission to read project sources does not justify loading them all into context. Existing declared dependencies may be installed when needed; adding a dependency, running suspicious install code, accepting supply-chain risk, or incurring a paid service remains separately governed.

Use workspace-write/permission roots narrowly enough to exclude drive roots, the user profile, unrelated repositories, personal/cloud-sync folders, browser data, school/financial/health files, downloads, photos and communications. Prefer a Cuddle Crew-only stable worktree parent or the active managed worktree as its session workspace; never widen to an application-wide or personal parent merely to avoid prompts. Command network access, GitHub, browser/search, MCP/apps and external SaaS are separate trust boundaries. Production deploys/data, DNS/domains, credentials/secrets, client-facing business or legal-policy meaning, irreversible external effects, material recurring cost, protected/shared history rewrites, and privileged execution of untrusted code remain Lauren gates.

If routine work still pauses, emit `PLATFORM_APPROVAL_STALL` with category `READ`, `WRITE`, `GIT`, `WORKTREE`, `TEST`, `NETWORK`, `TASK_MESSAGE`, `EXTERNAL_TOOL`, or `OTHER`; identify the attempted action, effective root/policy, why the platform gated it, and the smallest safe remediation. Inspect once, use task-ID/RUN fallback for uncertain messaging, and do not loop or bypass a denial. Repeated safe friction may emit `APPROVAL_FRICTION_IMPROVEMENT`; a newly supported granular root, permission profile, auto-review, trusted-command, network, background, messaging or external-tool control may emit `NEW_AUTONOMY_CAPABILITY`. Both are recommendations, not authority to widen access.

Use minimum privilege that supports useful autonomy. Local/background work can continue only while the applicable Codex process, host, workspace and connectivity remain available; prevention of idle sleep is a mitigation, not restart/sleep/logout survival. If workspace mode cannot support a recurring legitimate workflow, return `FULL_ACCESS_EVALUATION_REQUIRED` using TEMPLATES. Never silently select full access or weaken a high-risk gate.

## Role context lifecycle

### Project memory and role continuity

A logical role may last for the project while its physical Codex chat/task does not. Role continuity comes from Git, commits, branches/worktrees, PRs, exact-SHA CI, AGENTS, this guide, PROJECT_STATUS, TEMPLATES, relevant RUNs, approved business sources, architecture decisions and existing backlog/project records. This durable, auditable evidence is **project memory**. Reasoning and conversation inside one task are temporary **working memory**; they may be compacted, become stale or disappear. A compacted summary or predecessor receipt is navigation, never sole proof of current SHA, ownership, validation, review, authority or business truth.

At meaningful checkpoints apply the minimum durable-state test: if every current Codex conversation disappeared, could a fresh Orchestrator recover current main, authorized phase, active work/owner/branch/worktree, pending PR/CI/review, business blockers, user decisions and next authorized action? If not, repair PROJECT_STATUS and/or the applicable RUN before continuing. Important authorized decisions that must govern future work belong in the existing appropriate source, status, RUN, test or template; do not preserve every preference or full transcript. Promote one reusable lesson from a retiring task only when future recovery needs it.

### Rotation assessment

Consider physical-role rotation only with evidence of effective context saturation, excessive dependence on compaction, stale or contradictory assumptions, completed-history noise, navigation friction, resource inefficiency, context-related reliability degradation, or a major phase/release transition. Do not rotate by age, turn/chat count, generation cadence, model novelty or cosmetic preference. Infrequently at a major transition, after several completed items, on obvious degradation, and before the pre-launch comprehensiveness audit, ask whether context is current, focused, noncontradictory, efficient and recoverable from durable state. Post-launch, separately consider whether BUILD MODE should become OPERATIONS / IMPROVEMENT MODE; neither milestone automatically authorizes rotation.

When evidence warrants consideration, emit `ROLE_ROTATION_RECOMMENDED` using TEMPLATES. Compare `ROTATION_COST` and `EXPECTED_CONTEXT_BENEFIT` (LOW/MEDIUM/HIGH) plus initialization, routing, validation and information-loss risk; rotate only when expected benefit exceeds handoff cost. Prefer an idle/between-item point after durable state, Git/PR/CI and ownership are clear. Finish or checkpoint sensitive active coordination unless continuing the degraded task is less safe.

Distinguish `CONTEXT_PROBLEM` from `MODEL_CAPABILITY_PROBLEM`. For buried or noisy constraints, prefer a fresh same-capability context before a materially more expensive model. For clean context with genuinely difficult reasoning, adjust model/effort. When both apply, a fresh stronger successor may be appropriate; record `ROTATION_REASON` and `CONFIGURATION_ESCALATION_REASON` separately. Continuous improvement may report `CONTEXT_ROTATION_OPPORTUNITY`; new persistent-memory, context visibility, cloning/succession, routing/ACK, role or handoff primitives use `NEW_CONTEXT_MANAGEMENT_CAPABILITY` with simplification impact. Discovery never authorizes churn.

### Controlled role succession

Before replacement, checkpoint the applicable current main, work item, owner/task IDs, branch/worktree, base and current SHA, CI/review/Business Truth, blockers, user decisions, pending improvements and next authorized action in PROJECT_STATUS and/or the existing RUN. If another worker owns active implementation, it remains owner: preserve WORK_ITEM_ID, OWNER_TASK_ID, branch/worktree, base/current SHA, receipts, blockers and validation state. Orchestrator succession transfers coordination, not implementation ownership, and never creates a duplicate Implementer.

If an unsuffixed role rotates, treat it as generation 01 and name the first successor `CC — <ROLE> — 02`; do not retrofit existing names. Normally exactly one physical task is `ACTIVE` and canonical per logical role. Brief predecessor/successor overlap is allowed only for controlled handoff; independent duplicate coordinators return `DUPLICATE_LOGICAL_ROLE_DETECTED` and stop competing routing.

Where possible obtain the concise predecessor receipt in TEMPLATES, then initialize the successor from durable evidence. An Orchestrator normally reads AGENTS, ORCHESTRATION, PROJECT_STATUS, relevant current RUNs, current Git/GitHub state and only applicable active roadmap/business/architecture sources. Reviewer gets the exact current assignment/diff and authority; Sentinel reconstructs deterministic state with minimal history; Business Truth re-reads the hierarchy and applicable CURRENT / APPROVED sources and never transfers remembered rates/policies as authority. Do not copy the predecessor transcript, every historical RUN/phase, or all closed PR discussions.

Before making the successor canonical, run the reconciliation test in TEMPLATES: it must independently identify current main/phase, active work and owner, branch/worktree, CI, review, Business Truth, blockers and next authorized action consistently with durable evidence. Correct material conflicts before retirement. Record the returned successor task ID, safely test task-ID routing, obtain route-specific ACK where available, update the lightweight current-role pointer and preserve the complete RUN fallback. Names remain noncanonical and native messaging/ACK remains PARTIAL unless new platform evidence proves otherwise.

After verified state and routing, write one concise succession entry and mark the predecessor `ROLE_RETIRED`/historical. Retain searchable history for audit only; current agents use durable sources first. Before archive, apply the existing worktree-preservation procedure—status, branch/worktree, diffs, index/staged state, relevant blobs/commits and recovery proof—because archival may remove a managed worktree. Never archive meaningful unintegrated work as storage. Graceful receipt is optional: crash-only recovery must work from Git/GitHub, PROJECT_STATUS, RUNs, task state where available and authoritative sources.

Persistent Reviewer is a reusable entry/coordination identity; important assignments may still use fresh bounded review tasks for independence. Sentinel should carry almost no historical context, making replacement cheap when stale. Business Truth is highly replaceable because repository authority, not its memory, controls. Implementers remain disposable per work item. If one saturates or lacks capability, emit `IMPLEMENTER_HANDOFF_REQUIRED`, checkpoint the fields in TEMPLATES, stop duplicate ownership and recognize exactly one new owner. Rotation or handoff is control-plane work only and never authorizes a product item, pilot, deployment or provider mutation.

## One work item, one owner

Use an existing finding ID where available. Record WORK_ITEM, OWNER (task/agent ID), BASE_SHA, BRANCH/worktree, STATUS, and LAST_PROGRESS before substantial work. Duplicate ownership returns `DUPLICATE_WORK_DETECTED`; stop duplicate implementation until the Orchestrator resolves it. Only the Orchestrator edits the shared status ledger; workers report back.

Normal lifecycle: PLANNED → READY → ASSIGNED → IN_PROGRESS → IMPLEMENTED → IN_REVIEW → VERIFIED → COMPLETE. Use STOP_REQUESTED, BLOCKED, BLOCKED_BY_EXTERNAL_DEPENDENCY, WAITING_FOR_USER_DECISION, CHANGES_REQUESTED, DEFERRED, STALE_TASK, ABANDONED, or CANCELLED when needed. A waiting record names the dependency/decision, evidence, owner, and event that permits resumption; stop until that event instead of polling. `MESSAGE_TYPE: COMPLETE` is a worker's handback, not permission to mark the whole item complete.

For each authorized item:

1. Verify prerequisites and authority; classify risk; predict changed files/modules; state acceptance and relevant negative requirements.
2. Choose the smallest sufficient context, model/reasoning/speed, owner, fresh/reused role task, validation, Business Truth need, security review, independent review, and parallel safety.
3. Send the [assignment](TEMPLATES.md). Record its identity before retrying delivery. Monitor meaningful progress and route blockers without repeated polling.
4. Receive the actual diff/final SHA and criterion-by-criterion evidence. Investigate `CHANGE_SURFACE_DEVIATION` before accepting a materially larger diff.
5. Inspect required CI directly; PASS routes to review, FAIL to Implementer/Sentinel. A missing required run is PENDING, never NOT_APPLICABLE.
6. Review the precise artifact. Route bounded corrections; recheck prior findings and fix-caused regressions. Put optional observations in the existing phase backlog; they do not become authorized work.
7. Reconcile final SHA, CI SHA, reviewed SHA, scope, business truth, and blocking findings. Update durable evidence/status, close the item, and stop or continue only already-authorized work.

Code written is not done. COMPLETE requires authorized scope and acceptance/negative criteria satisfied, relevant passing tests and required CI, known exact final SHA, no unauthorized files or blocking findings, appropriate independent approval, Business Truth when required, no new secrets, updated status/relevant docs, understandable Git state, and practical rollback where applicable. Keep IMPLEMENTED, REVIEWED, VERIFIED, MERGED, RELEASED, and DEPLOYED distinct. Completion of an implementation item need not imply merge/deployment; report each separately.

## Adaptive resources and context

Select the **most cost-efficient sufficiently capable configuration for each task**. Quality and reliability come first. Model, reasoning effort, and speed/priority are three independent levers, with no fixed model hierarchy or preference for maximum effort or fastest execution. Long work alone does not justify a frontier model. Role settings and historical pilot recommendations are starting points, never locks.

Before meaningful delegation assess TASK_COMPLEXITY (LOW/MEDIUM/HIGH/EXCEPTIONAL), AMBIGUITY, RISK (LOW/MEDIUM/HIGH/CRITICAL), DETERMINISM, CROSS_FILE_REASONING, CROSS_SYSTEM_REASONING, CONTEXT_DEMAND, REVERSIBILITY, TIME_SENSITIVITY and COST_SENSITIVITY (other scales LOW/MEDIUM/HIGH), plus expected iterations and review importance when useful. Then record MODEL, REASONING, DESIRED_SPEED and WHY in the assignment. A concise justification suffices for trivial work.

| Task class | Model choice | Reasoning choice | Speed choice |
| --- | --- | --- | --- |
| Inventory, mechanical docs, deterministic validation/status | Lowest-cost capable live option; tooling first | Low when explicit/deterministic | Economical/normal unless delay blocks authorized work |
| Bounded implementation, normal review, ordinary coordination | Capable balanced option | Usually medium | Economical/normal; faster only for justified critical-path iteration |
| Ambiguous debugging, architecture, security, complex integrations | Stronger capability when the evidence requires it | High/very high only for the unresolved complexity | Independently assess latency benefit; risk alone does not justify a speed premium |
| Exceptional tangled failure or one-time architecture synthesis | Frontier only when task demands or failed smaller configurations justify it | Smallest sufficient effort | No automatic premium |

Recheck currently exposed models/efforts and account constraints. Do not infer exact prices or executing configuration from a role name. Example initial assignments: ordinary Orchestrator/Reviewer/Business Truth may use Terra/medium; deterministic Sentinel may use Luna/low. Sol, Astra and other available choices have no inherent precedence. Reassess every meaningful assignment, including reviews and verification.

Lauren authorizes the Orchestrator to adjust resources within authorized scope. Use the smallest change likely to help: MODEL_ESCALATION, EFFORT_ESCALATION or SPEED_ESCALATION for repeated failures, contradictory technical evidence, larger-than-expected scope, architecture/security uncertainty, or persistent unclear failures. Workers report the evidence; the Orchestrator routes the adjustment. Difficulty never expands scope or business authority.

Actively use MODEL_DEESCALATION, EFFORT_DEESCALATION or SPEED_DEESCALATION once architecture is settled, scope narrows, or only mechanical corrections, deterministic tests, status, or targeted fix verification remain. Do not keep Ultra or a premium model engaged because an earlier stage needed it. Record material overrides as PREVIOUS_CONFIGURATION, NEW_CONFIGURATION, REASON; no detailed quota ledger.

Platform limits must be explicit. Native create currently constrains explicit model selection to a user-requested named model; otherwise omit that field, request supported effort, and use a configured follow-up turn through `send_message_to_thread` where supported. That follow-up accepts model/effort overrides; it does not prove an in-flight turn changed. Do not send duplicate work just to change settings. If in-place change is unavailable, compare continuing against a fresh task's capability/cost gain minus handoff cost. When a fresh task wins, preserve work item/message identity, evidence, branch/worktree, base/final SHA, current diff, blockers and validation, stop the old owner, then transfer ownership. Do not restart from zero.

The inspected create/send tools expose no speed/service-tier setter or authoritative speed readback. Record DESIRED_SPEED separately from ACTUAL_SPEED: UNKNOWN; record unsupported control as a limitation, retain host default, and do not claim economical execution was applied. Collaboration also offers no speed selector. Use a supported future setter or a brief owner UI adjustment only when materially needed; no global config rewrite or premium purchase. [Runtime evidence](RUNS/2026-09-09-reconciliation.md) records current limitations.

Learn qualitatively per task class: retain cheaper configurations that succeed; raise only a failing class's baseline. At meaningful handoffs notice premium models running tests/status, excess effort, repeated context reloads, duplicate/idle agents, repeated full reviews, unjustified speed premiums, or cheap failures that should have escalated sooner. Adjust future routing; do not build token analytics or periodic token-consuming monitors.

## Git, parallelism, CI, and review

Default `PARALLEL_SAFE: NO`, **one active write-heavy Implementer**, including control-plane writers. Independent writers normally use separate Codex/Git worktrees, isolated checkouts/branches or equivalent safe sandboxes; never share one mutable checkout. A branch name alone is not filesystem isolation. Concurrent implementation requires independent non-overlapping write surfaces, settled interfaces, satisfied dependencies, isolated worktrees and a known merge strategy whose integration/review cost does not erase the benefit. Serialize manifests/lockfiles, shared rules/types/schemas/styles/routes/utilities/config/CI. Subagents share their parent's filesystem; spawning one does not create isolation. The canonical checkout is never a writer-swarm scratchpad; dirty-state protections remain controlling.

State READ_SCOPE separately from WRITE_SCOPE and FORBIDDEN_WRITE_SCOPE where practical. Permit relevant read discovery; meaningful expansion of expected writes requires CHANGE_SURFACE_DEVIATION with reason, affected paths and acceptance/dependency impact before proceeding, resolved by Orchestrator within existing authority. Adjacent discovery never silently becomes cleanup. List lightweight DEPENDENCIES by work-item ID; start a dependent worker only when its prerequisites are satisfied, not to fill capacity. Orchestrator/designated integration owner alone integrates into the target under existing Git/PR/CI/review gates; workers never race merges.

Read-heavy reconnaissance, source research, security/accessibility inspection, dependency/log diagnosis, architecture critique and regression analysis are preferred parallel opportunities when independently useful and easy to synthesize. Distinct read-only quality specialists may examine the same artifact when justified; Orchestrator deduplicates findings. Before each additional agent weigh wall-clock savings, independent quality, risk reduction or specialization against extra model/tool/CI usage and synthesis/integration cost. Weak benefit means no spawn; platform concurrency is a ceiling, not a target. Apply adaptive model, effort and desired speed independently to every role and optional mode.

Before work and review compare assigned BASE_SHA with actual source and current base. Material divergence returns `STALE_BASE_DETECTED`; decide continue/refresh/replace/restart from evidence. Shared-history rebase/amend still requires explicit authorization under CONTRIBUTING. Never use a stale dirty local main as a fresh task base. Select a verified remote ref/SHA explicitly for native worktree creation, then verify the resulting HEAD before executing.

Use focused `codex/*` branches, exact-path staging and one-purpose commits. Preserve unrelated changes, source branches, and useful abandoned work. No reset/clean/history rewrite/force-push to make a workspace convenient.

Routine first-party CI uses the existing **Validation** workflow: open/update a same-repository PR (including a draft) to validate its exact head; trusted `main` pushes also run automatically. Feature-branch push alone is not a trigger. Do not add duplicate push runs or auto-approval bots merely to avoid creating a PR.

Keep `contents: read`, credential persistence off, pinned Actions, synthetic short-lived failure artifacts, write/indexing gates off, and no production secrets/deployment environment. Unknown fork/contributor code needs the platform's approval policy plus security review before execution; return `GITHUB_ACTION_APPROVAL_REQUIRED` with the actual reason. Never use `pull_request_target` to run untrusted code with elevated authority. Untrusted caches/artifacts cannot become trusted release inputs.

Workflow/security-boundary changes are HIGH risk even on a Codex branch: record WHY, TRIGGERS, PERMISSIONS, SECRET ACCESS, THIRD-PARTY ACTIONS, EXTERNAL SIDE EFFECTS and independently review them. Do not widen token permissions to fix an unexplained permission failure. Preserve concurrency cancellation only for superseded validation, not unrelated releases.

Sentinel/Orchestrator may cancel a positively identified superseded validation run when useful within an authorized task. Never cancel the only required evidence for the current SHA. Prevent CI/bot-comment loops: do not trigger work from the agent's own status comments or repeatedly write commits merely to update their own SHA. Native GitHub protection recommendations, benefits, plan/cost uncertainty and maintenance are retained in the [bootstrap security table](RUNS/2026-09-09-bootstrap.md#github--ci-audit); they are recommendations, not authorization to enable them. Unknown code never receives production secrets, write tokens, deployment or destructive privileges to bypass approval.

The meaningful hosted job is `validate` in Validation; inspect current names/rules rather than assuming enforcement. Inspect checks/run logs by exact source SHA and URL. Initial PR review must establish HEAD_SHA = CI_SHA = REVIEWED_SHA. A later merge commit is a new SHA: inspect its integration diff, run required merge validation/CI, and bind approval to that result before calling it verified. Documentation/status commits also change SHA; obtain required CI for the final commit.

No universal auto-merge. Retain the separately authorized normal `--no-ff` merge-only process and source branches from CONTRIBUTING. Merge only when scope, business truth, checks, relevant review, conflicts, and deployment coupling are resolved; merge does not deploy here.

Implementer cannot self-satisfy independent review. Default review budget is one meaningful independent review plus targeted fix verification. First review covers the assigned scope and actual commit/diff. Corrections get bounded prior-finding and fix-regression review; optional ideas never block closure. Material post-review edits invalidate relevant review and require renewed SHA-bound checks. A second full review needs new evidence and a stated reason (such as changed scope or compromised independence). If bounded corrections stop converging, diagnose/escalate or block on a concrete decision instead of looping indefinitely. Close when required findings and criteria pass.

Calibrate tests to change size, risk, reversibility, affected surface and previous failures. Use focused checks while editing; repeat broad suites only for new evidence or required gates. CONTRIBUTING's full branch/merge validation remains required; proportionality never waives a repository gate.

### Optional bounded modes

- **Plan critic:** for unusually difficult/high-risk work, one fresh critique before expensive implementation may check boundaries, dependencies, interfaces, collisions, omissions and simpler alternatives. Routine work needs no extra plan reviewer.
- **BEST_OF_N_CANDIDATE:** recommend only for rare high-value work where ambiguity, architecture or difficult correctness tradeoffs justify duplicated implementation cost. Candidates require separate worktrees, bounded scope and the write-concurrency/usage gates. A fresh Reviewer compares correctness, simplicity, maintainability, architecture, tests, business compliance and risk; one integration owner selects the result. Never use for routine features, docs, mechanical or deterministic work.
- **SPIKE:** use read-only research or an isolated worktree for architecture/UI alternatives, feasibility, technology evaluation or debugging hypotheses. Return recommendation/evidence; a spike does not change product scope, policy, production architecture or implementation authorization.

Classify failures: NEW_REGRESSION, PRE_EXISTING_FAILURE, FLAKY, ENVIRONMENT_FAILURE, UPSTREAM_PROVIDER_FAILURE, UNKNOWN. Preserve evidence; diagnose cause. Do not weaken assertions, types, lint/security rules, counts, snapshots, or timeouts to get green. Unrelated historical failure is not automatically repair scope, but cannot be represented as passing required validation.

## Continuous improvement without scope expansion

### Workflow promotion and experiments

New recurring workflows earn complexity: **1. ordinary bounded task + standing instructions → 2. one reusable specialized role after a repeated clean boundary → 3. ordered multi-pass workflow after distinct recurring passes prove useful → 4. parallel execution only after the serial workflow is stable and parallelism demonstrates value**. Do not recreate established persistent roles or start a new workflow with an agent team. Before promoting a role, skill or specialized agent ask whether it recurs, its boundary is stable, inputs/outputs predictable, reuse reduces repeated explanation, and scope stays narrow enough for reliability. Mostly yes permits consideration; otherwise keep an ordinary task. Repeated lessons may belong in a map rule, orchestration rule, template, test, helper, role or skill; one-off events do not earn permanent process.

Before permanent adoption of a new technique, define a hypothesis, test one authorized bounded low/medium-risk task, and compare quality, usage, human intervention, coordination complexity and failure modes. Retain only a meaningful improvement. Distinguish OFFICIAL_CURRENT_PLATFORM_BEHAVIOR, COMMUNITY_PRACTICE, ANECDOTAL_REPORT and PROJECT_EMPIRICAL_EVIDENCE; cite source/date and limits. Community inspiration cannot override current official guidance, actual runtime/project evidence or business authority. Capability-detect before depending on any behavior. The [bounded research addendum](RUNS/2026-09-09-multi-agent-practices.md) records this pass without reopening coverage 1–106.

### Infrastructure boundaries

Existing tasks/IDs, PROJECT_STATUS, RUNs, Git worktrees/branches and GitHub PR/CI suffice. No SQLite/Redis/RabbitMQ/Postgres queue, bespoke scheduler or task server; reconsider only after measured failures establish need and separate authorization. MCP is an integration/capability boundary, not inherent locking, retries, process supervision, leases, transactional concurrency or merge resolution. Explicit ownership remains necessary.

Native Codex subagent routing is primary for new bounded work. Separate desktop/task-ID routing is optional for deliberately persistent physical conversations, not a prerequisite for an Implementer or Reviewer. **agent-talk: EVALUATE LATER**, only if native subagents plus durable RUN recovery prove insufficient through measured evidence. Before any later adoption evaluate project compatibility, current Codex version support, supply chain, hooks/daemon, relay trust/privacy, encryption/keys, maintenance, failure modes and operating burden. **tmux/CLI: optional later** for demonstrated shell-debugging, observable-pane or direct-process workflows. No installation or new agent infrastructure is authorized by these rules.

### Opportunity discovery

During meaningful work and milestone reviews, actively notice useful improvements to orchestration, website, environment, GitHub/CI, security, business operations and integrations. Include functionality, navigation, mobile/accessibility, SEO/robots/sitemap/structured data, performance/media, privacy, client onboarding/forms/quotes/error recovery, business consistency, testing, release/recovery, automation, owner workload, client trust and cost when relevant. This is a standing recommendation duty, not a full audit on every task or implementation authority.

Use HIGH_VALUE_IMPROVEMENT_FOUND for material safety/security, business-error prevention, owner-workload or client-experience benefits. Use ADJACENT_OPPORTUNITY when authorized work makes a useful improvement unusually cheap; report INCREMENTAL_EFFORT, BENEFIT, RISK and SCOPE_EFFECT. Route findings to Orchestrator. Only a tiny reversible internal improvement that directly supports approved scope may proceed under existing technical authority; client/business/security/cost/architecture changes need their proper authorization. Never create another Implementer from a finding alone.

For meaningful recommendations use the compact [recommendation template](TEMPLATES.md#improvement-recommendation): what/why/evidence/expected benefit, type, value, effort, risk, cost, maintenance, dependencies, timing and AUTHORIZED_NOW (usually NO). Deduplicate against the existing phase backlog before adding an accepted recommendation there; orchestration-only observations may stay in the current RUN. Retain source/evidence and owner/decision needed; close, defer or supersede stale ideas. Do not create a competing roadmap or turn optional findings into completion blockers.

Apply a value test before recommending AI, automation, prediction, dynamic behavior, background agents or abstractions: does it materially improve correctness, safety, client experience, owner workload, efficiency, reliability, maintainability, personalization, decision quality, cost or error prevention enough to justify complexity, risk and maintenance? Prefer deterministic rules when better. No AI for its own sake. Reuse the integration inventory; prefer official APIs, server-side secrets, consistency, idempotency, graceful failure, privacy and recovery. Detect duplicate entry/subscriptions and unnecessary model effort, CI runs, API calls, storage or manual reconciliation without changing policy or providers.

At meaningful milestones, review major quality/operational gaps across the areas above. Before public launch, recommend a dedicated full client-journey and cross-cutting audit using the existing 12G/release contracts, including browser/mobile/accessibility, contact information, policy/pricing consistency, media, consent/analytics, forms/integrations/error states, production configuration and rollback. An audit does not authorize launch. After launch, prioritize observed errors, client friction, support/admin burden, performance, security advisories, provider changes, accessibility findings and authorized analytics over speculative features.

During those same bounded reviews, surface NEW_CAPABILITY_OPPORTUNITY with WHAT_CHANGED, BENEFIT, MIGRATION_EFFORT and CAN_EXISTING_FALLBACK_BE_SIMPLIFIED. Recheck task IDs, ACK/fallback reliability, handoff length, model/speed controls and costs, worktree safety, review efficiency, status accuracy, role usefulness and native GitHub protections. Notice relevant API/Action/runtime/dependency deprecations, provider removals and obsolete workarounds. Do not rebuild the control plane for every new feature; material changes become separately authorized work. No background polling, automatic provider changes or subscription purchases.

Use NEW_ORCHESTRATION_OPPORTUNITY in this same recommendation mechanism for worthwhile patterns: WHAT, SOURCE_TYPE (OFFICIAL / COMMUNITY / PROJECT EXPERIENCE, with the finer evidence label above), WHY_IT_MAY_HELP, EXPECTED_BENEFIT, EXTRA_COMPLEXITY, EXTRA_MODEL_CI_USAGE, SECURITY_SUPPLY_CHAIN_EFFECT, PILOT_PROPOSAL and AUTHORIZED YES/NO. No auto-adoption or second improvement system. Ask whether it is actually better, worth its cost/maintenance, and authorized; smart need not mean AI and comprehensive need not mean complicated.

Optional recommendations never prevent PROJECT_COMPLETE_FOR_CURRENT_SCOPE. Finish the authorized item, surface only worthwhile next opportunities, and stop when no approved work remains. Continuous improvement must retain an explicit end to current scope.

## Messaging, durable evidence, and recovery

Use native discovery/status/read/send/create tools when exposed; discover actual names rather than inventing APIs. In this app, top-level task tools include `list_projects`, `list_threads`, `read_thread`, `create_thread`, `send_message_to_thread`, and `wait_threads` in `mcp__codex_app`. Native subagents use `collaboration` spawn/send/followup/list/interrupt. Do not confuse either mechanism with a guaranteed-delivery queue.

Communicate at meaningful checkpoints: assignment/ACK, interface clarification, blocker, scope deviation, implementation complete, review findings and verification result. Avoid constant worker-to-worker chatter. Unbounded recursive consultation returns CONTEXT_POLLUTION_RISK; Orchestrator restores clear ownership and bounded questions, not another supervising agent.

For a top-level task, TASK ID is the canonical machine-routing identity when available and TASK NAME is a human-readable/discovery label. Pending `clientThreadId` is a setup token, not a ready `threadId`; resolve it from actual returned/listed identity before sending. For a native subagent, its returned runtime agent/thread identity is canonical for that bounded assignment; it is not a top-level task ID and must never be fabricated. Record its parent Orchestrator identity, role, work item, base, branch/worktree and returned identity in the RUN. Names are labels only. Keep runtime identities in dated evidence, revalidate where the interface permits, and mark persistence UNKNOWN/runtime-only unless the platform guarantees durability. Only use returned verified deeplinks; never invent a URL scheme.

Top-level native task messaging and end-to-end acknowledgement are **PARTIAL** based on the post-bootstrap approval-gated ACK test. API send acceptance is not proof of delivery/execution. Native subagent creation/result return is a separate tested route; record its actual returned identity and result rather than claiming a top-level ACK. Subagent success does not upgrade top-level-task delivery guarantees. Use WORK_ITEM and MESSAGE_ID for idempotency: duplicate assignments return existing state, never a second implementation. A writer acknowledges owner/base/scope before edits in its returned receipt or durable RUN. Messages carry no secrets and cannot grant more authority.

If a top-level-task delivery is blocked, unreliable, approval-gated, ambiguous or unacknowledged, inspect recipient state once and use a bounded wait only when useful. If native subagents are available, use one rather than retrying top-level provisioning; otherwise switch to the prepared RUN recovery path or the eligible parent-writer fallback. Blind retries are prohibited; resend only after a concrete state change, with the same message ID and duplicate check. Prepare the complete ready-to-use assignment in the existing RUN: execution mechanism, role, task/runtime identity if returned, parent identity, model/reasoning/speed (desired versus known actual), work item, assignment/scope, truth paths, base SHA, branch/worktree, acceptance, validation, and report-back destination. Include current diff/blockers for recovery. The RUN preserves a task loss or human transfer; it never claims to have created a missing worker. No broker, scheduler, permanent heartbeat or extra handoff directory.

[PROJECT_STATUS](PROJECT_STATUS.md) holds current operational state only. For substantial delegated work keep one small `RUNS/<work-item>.md` using [TEMPLATES](TEMPLATES.md), or reference an equivalent existing phase report. Retain base/final SHA, owner/task, branch, authorization/scope, model/reasoning/speed recommendation and actual-if-known, overrides, validation/CI/review/Business Truth, limitations and rollback. Record material progress only; archive no chat transcript. Evidence can identify its own containing commit via Git history instead of a circular self-SHA field.

| Failure | Recovery |
| --- | --- |
| Missing/failed task or tool outage | Mark BLOCKED/ABANDONED as appropriate; inspect branch, commits, diff and evidence; preserve good work; use the RUN fallback. Resume only with one recognized owner. |
| Stale task/base/status | Mark STALE_TASK or STALE_BASE_DETECTED; reconcile actual Git/task evidence before resuming; update cache without reopening completed phases. |
| Dirty branch | Preserve unrelated state; exact-scope staging or fresh verified worktree. No automatic stash/reset/clean. |
| CI/review failure | Route evidence to owner; corrections then prior-findings/fix-regression verification; PENDING/FAIL never VERIFIED. |
| Business/requirement conflict | Block dependent work and send one concise evidence-backed decision request; batch related nonurgent decisions. |
| Production incident | Contain, preserve safe evidence, restore within authority, diagnose, validate, record prevention in existing incident mechanism. No unrelated cleanup; suspected security incident requires Lauren. |

On cancellation record STOP_REQUESTED and send TASK_CANCELLED through supported controls. Only record STOP_CONFIRMED after explicit completion/stop evidence and inspection of relevant Git state; a queued request or accepted send is not confirmation. If control is blocked, keep STOP_REQUESTED, use the durable fallback, preserve evidence and prevent competing writes. Before changing, reassigning or archiving the stopped worktree, confirm execution has stopped. Before archiving meaningful unintegrated work, capture branch/worktree identity, HEAD, status, staged and unstaged diff, tracked/index state and relevant blob/commit hashes; preserve necessary untracked work outside the managed worktree in an approved safe location and verify recovery is possible. Archival may clean a managed worktree; it is not storage. If preservation is uncertain, leave the task stopped and unarchived. Never clean or adopt preserved work without authority. A replacement Orchestrator reconstructs from Git, status, RUN/phase records, branches and native task state, replaces the runtime routing record, reconciles unresolved ownership and preserves existing authority. It never depends on one chat's memory.

At meaningful reconciliation/handoff/closure check: one owner and no duplicate implementation; active branch exists; PROJECT_STATUS matches Git; stale base resolved; COMPLETE has no blocking review; VERIFIED has passing required CI; final/review/CI SHAs correspond; no business conflict bypassed; routing IDs still valid; expensive model/effort/speed remains justified. This is a periodic operational self-audit during authorized work, never a background loop or full audit after trivial actions. If role hops, review loops, context loading, resource cost or documentation exceed value: SIMPLIFY.

After substantial work also ask: did implementation match Lauren's intent and preserve correct business behavior; did assumptions or write scope change; is PROJECT_STATUS current; is there a repeated reusable lesson; did multi-agent usage earn its cost? Record only meaningful answers in the existing RUN/status. This is post-work orchestration reconciliation, not another whole-code review or restart of completed reconciliation. RUN evidence supports recovery after task loss, restart, messaging failure, context loss, abandonment, archival or interruption; preserve useful receipts/artifacts, never private reasoning, full transcripts or massive logs.

Use PROJECT_COMPLETE_FOR_CURRENT_SCOPE only when all work in the authorized scope has no remaining blocking item; distinguish completed orchestration from application NO-GO. NO CHANGE RECOMMENDED is valid when evidence supports it. Otherwise use WAITING_FOR_USER_DECISION or BLOCKED_BY_EXTERNAL_DEPENDENCY as appropriate, explain the concrete next action, and stop. UNEXPECTED_FINDING never creates a roadmap item, broadens a phase, starts another Implementer or authorizes unrelated refactoring; nonblocking findings use the existing backlog.
